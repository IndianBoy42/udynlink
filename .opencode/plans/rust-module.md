# Rust Module Support for udynlink — Detailed Sub-Plan

**Status:** Draft — Awaiting user review  
**Last updated:** 2026-05-26

---

## 1. Goal

Enable developers to write `no_std` Rust crates, compile them, and produce udynlink-compatible `.bin` modules that the existing C loader can load and execute on any supported Cortex-M target.

**Non-goal:** Extending the C loader to support new relocation types. The output must be a valid UDLM binary consumable by the unmodified `udynlink_load_module()`.

---

## 2. Context for Implementation Agents

### 2.1 How the C Toolchain Works (Pipeline to Replicate)

1. **Compile** with GCC:
   ```
   arm-none-eabi-gcc -fPIE -msingle-pic-base -mno-pic-data-is-text-relative \
       -mcpu=cortex-m4 -mthumb -ffunction-sections -fdata-sections -Os
   ```
   This makes the compiler:
   - Access global data via the GOT (Global Offset Table)
   - Use `r9` as the static base register pointing to the GOT/LOT
   - Emit `R_ARM_GOT_BREL` relocations for every data access

2. **Wrap exports** with assembly prologues (generated by `asm_template_armv7m.tmpl`):
   ```asm
   myfunc:
       push    {r9, lr}
       push    {r1}
       ldr     r1, .L1myfunc
       ldr     r9, [r1]          ; Load LOT base from UDYNLINK_LOT_BASE_ADDR
       pop     {r1}
       bl      __wrapped_myfunc  ; Call actual function
       pop     {r9, pc}
   .L1myfunc: .word 0x20000000   ; Configurable
   ```

3. **Link** with `code_before_data.ld` (origin 0x0):
   - `.text` at 0x0, `.data` immediately after, `.bss` after `.data`
   - `.got` is placed in `.text` or adjacent (so code→got offsets are fixed)

4. **Post-process** ELF (in `scripts/mkmodule`):
   - Read `.text`, `.data`, `.bss` sections
   - Parse symbols: exported (defined, global), external (undefined, global), local
   - Parse relocations: `R_ARM_GOT_BREL` (LOT), `R_ARM_ABS32` / `R_ARM_TARGET1` (data)
   - Build LOT: one entry per unique relocated symbol
   - **Patch code**: for every `R_ARM_GOT_BREL`, replace the GOT offset in the instruction with the corresponding LOT offset
   - Build symbol table (with type/location encoding)
   - Assemble binary: header + relocations + symbol table + code + data

5. **At load time** (in `udynlink.c`):
   - Allocate RAM: LOT entries at start, then `.data`, then `.bss`
   - Copy sections as needed (depends on load mode)
   - Apply relocations: patch LOT entries with absolute addresses
   - Resolve extern symbols via host callback

### 2.2 Key Data Structures

```c
// Module header (36 bytes, ABI v2.0)
typedef struct {
    uint32_t sign;              // 'UDLM'
    uint16_t mod_version;       // Module ABI version
    uint16_t udynlink_version;  // Loader ABI version (2.0)
    uint16_t arch_tag;          // Target architecture + float ABI
    uint16_t num_lot;           // Number of LOT entries
    uint16_t num_rels;          // Number of relocations
    uint16_t num_deps;          // Dependencies
    uint32_t symt_size;         // Symbol table size in bytes
    uint32_t code_size;
    uint32_t data_size;
    uint32_t bss_size;
    uint32_t deps_strtab_size;
} udynlink_module_header_t;
```

### 2.3 What Makes Rust Different

| Aspect | C (GCC) | Rust (rustc / LLVM) |
|--------|---------|---------------------|
| PIC flags | `-fPIE -msingle-pic-base -mno-pic-data-is-text-relative` | `-C relocation-model=pic/pie/ropi/rwpi/static` |
| Data access | GOT via `r9` (R_ARM_GOT_BREL) | Depends on model: GOT via PC-relative (PIC), `r9`-relative (RWPI), or absolute (static) |
| GOT/LOT location | In `.text` or adjacent, accessed via `r9` | Varies by model |
| Relocations | `R_ARM_GOT_BREL`, `R_ARM_ABS32`, `R_ARM_TARGET1` | LLVM generates different relocation types depending on model |
| Symbol naming | Plain C names (or objcopy renamed) | Rust mangled by default; need `#[no_mangle]` |
| Initializers | `__init_array` for C++ | Rust `static` initializers are const-evaluated; no dynamic init needed in `no_std` |
| Vtables | C++: handled by C toolchain | Rust: `dyn Trait` generates vtables in `.data` with absolute addresses (non-PIC, rust#54431) |

### 2.4 Critical Constraint

The existing udynlink loader handles these relocation patterns:
- **LOT relocations** (`lot_offset < num_lot`): patch a LOT entry with an absolute address
- **Data relocations** (`lot_offset >= num_lot`): patch a `.data` word with an absolute address or offset
- **Flagged relocations**: `(1<<31)` for data section base offset, `(1<<30)` for code section base offset

The Rust post-processor MUST produce relocations that the existing loader understands.

## 3. Phase 0: Investigation Spike

**Goal:** Determine which Rust relocation model produces post-processable relocations.

**Agent:** `search` + `shell` (fast, read-only)

### 3.1 Spike Experiments

Create a minimal Rust program:
```rust
#![no_std]
#![no_main]

static mut COUNTER: u32 = 0;
static MESSAGE: &[u8] = b"hello\0";

#[no_mangle]
pub extern "C" fn add(a: u32, b: u32) -> u32 {
    unsafe { COUNTER += 1; }
    a + b + 42
}
```

Compile with each model and inspect:
```bash
# Model 1: static
rustc --target thumbv7em-none-eabihf -C relocation-model=static -C opt-level=s

# Model 2: pic
rustc --target thumbv7em-none-eabihf -C relocation-model=pic -C opt-level=s

# Model 3: pie
rustc --target thumbv7em-none-eabihf -C relocation-model=pie -C opt-level=s

# Model 4: ropi-rwpi
rustc --target thumbv7em-none-eabihf -C relocation-model=ropi-rwpi -C opt-level=s -C codegen-units=1
```

For each, run:
```bash
arm-none-eabi-readelf -r output.elf    # Show relocation types
arm-none-eabi-readelf -S output.elf    # Show sections (look for .got, .got.plt)
arm-none-eabi-objdump -d output.elf    # Disassemble to see how globals are accessed
```

### 3.2 Expected Outcomes

The spike must answer:
1. **Which model generates relocations in the ELF's relocation table?** (Static model may not generate any)
2. **What are the exact relocation type strings?** (e.g., `R_ARM_GOT_BREL`, `R_ARM_ABS32`, `R_ARM_SBREL32`, etc.)
3. **Is there a `.got` section?** Where is it located relative to `.text`?
4. **How does the assembly access globals?** PC-relative load? r9-relative? Immediate absolute?
5. **Does rust-lld successfully link each model?**
6. **What happens with the `#[udynlink_export]` proc-macro approach?**

### 3.3 Go/No-Go Decision

Based on spike results, choose the best model:
- **If `pic` generates `R_ARM_GOT_BREL` or compatible types**: Use `pic`. Post-processor patches code the same way mkmodule does.
- **If `pic` generates a different but mappable relocation type**: Map it in post-processor.
- **If `pic` generates no relocations and uses absolute immediates**: Reject `pic`.
- **If `static` generates no relocations**: Reject `static`.
- **If `ropi-rwpi` works without bugs**: Consider using it and modifying the loader (ONLY if user approves).
- **If none work**: We must extend the C loader OR restrict what Rust code can do (e.g., no globals).

## 4. Phase 1: `udynlink-module` Runtime Crate

**Goal:** Provide the proc-macro and runtime support for writing udynlink modules in Rust.

**Agent:** `agent` (multi-file Rust crate)

### 4.1 Crate Structure

```
crates/udynlink-module/
├── Cargo.toml
├── src/
│   ├── lib.rs          # Re-exports, panic handler, core types
│   └── macros.rs       # #[udynlink_export], #[udynlink_extern]
```

### 4.2 `#[udynlink_export]` Proc-Macro

Transform a function definition into:
1. An exported wrapper function (the name the host calls)
2. The actual function (renamed internally)

**Input:**
```rust
#[udynlink_export]
pub extern "C" fn hello(arg: i32) -> i32 {
    arg + 42
}
```

**Expanded:**
```rust
#[no_mangle]
pub extern "C" fn hello(arg: i32) -> i32 {
    // Prologue: save r9, load LOT base
    unsafe {
        let lot_base: u32;
        core::arch::asm!(
            "push {{r9, lr}}",
            "ldr r9, ={base}",
            "bl {inner}",
            "pop {{r9, pc}}",
            base = const 0x20000000,  // Will be patched by linker/post-processor
            inner = sym __udynlink_inner_hello,
            options(noreturn)
        );
    }
}

#[no_mangle]
#[link_section = ".text"]
extern "C" fn __udynlink_inner_hello(arg: i32) -> i32 {
    arg + 42
}
```

**Issue:** The inline asm prologue above won't work as written because it needs to pass arguments and return values correctly. A better approach is to implement the prologue in a `.s` file generated by the build tool (just like C does), OR use a pure-Rust approach:

```rust
#[no_mangle]
pub extern "C" fn hello() {  // same ABI
    unsafe {
        core::arch::asm!(
            "push {{r9, lr}}",
            "push {{r0, r1, r2, r3}}",  // Save args if needed
            "ldr r9, =__udynlink_lot_base_addr",
            "pop {{r0, r1, r2, r3}}",   // Restore args
            "bl {inner}",
            "pop {{r9, pc}}",
            inner = sym __udynlink_inner_hello,
            options(noreturn)
        );
    }
}
```

Actually, preserving all argument registers and calling conventions is architecture-specific and fragile. **Recommended:** The proc-macro generates a separate assembly `.s` file for each export, just like the C toolchain does. The `.s` file contains the prologue/trampoline. The Rust source just needs `#[no_mangle]`. This is what `mkmodule` does for C.

**Revised `#[udynlink_export]` design:**
```rust
#[udynlink_export]
pub extern "C" fn hello(arg: i32) -> i32 {
    arg + 42
}
```
The proc-macro:
1. Keeps `hello` with `#[no_mangle]` but adds a `#[link_name = "__udynlink_inner_hello"]` rename
2. Adds metadata to a `.udynlink.exports` custom section: `"hello\0__udynlink_inner_hello\0"`
3. The post-processing tool reads this section and generates `hello_prologue.s`

This decouples Rust compilation from assembly generation.

### 4.3 Panic Handler

Required for `no_std` binaries:
```rust
#[panic_handler]
fn panic(_info: &core::panic::PanicInfo) -> ! {
    loop {}
}
```

### 4.4 `#[udynlink_extern]` for Host Imports

Allow Rust modules to call host-provided functions:
```rust
#[udynlink_extern]
pub fn printf(fmt: *const u8, ...) -> i32;
```

The proc-macro marks this as `STB_GLOBAL` and `SHN_UNDEF` in the symbol table.

### 4.5 No `alloc` by Default

`udynlink-module` is `no_std` and `no_alloc` by default. Host can export an allocator if desired.

## 5. Phase 2: Standalone Post-Processing Tool (`rust2udynlink`)

**Goal:** Convert a Rust ELF into a UDLM binary.

**Agent:** `agent` (Rust CLI tool, or Python tool built on `udynlink_utils.py`)

**User preference:** Standalone tool first. A Rust-based tool is most natural.

### 5.1 Command-Line Interface

```bash
rust2udynlink \
    --target cortex-m4f \
    --lot-base 0x20000000 \
    --bin-name module.bin \
    --gen-header module_data.h \
    target/thumbv7em-none-eabihf/release/my_module
```

### 5.2 Processing Pipeline

Inspired by `scripts/mkmodule`:

1. **Read ELF**
   - Parse `.text`, `.data`, `.bss`, `.rodata`
   - Note: `.rodata` in Rust may contain string literals and const data. In the C toolchain, `.rodata` is merged into `.text`. The post-processor may need to merge `.rodata` into `.text`.

2. **Read symbols**
   - From `.udynlink.exports` section (proc-macro output): get exported function names and inner names
   - From ELF symbol table: classify as exported, external, local
   - Demangle Rust names for readability (but keep original mangled names in binary)

3. **Read relocations**
   - Parse relocation sections from the ELF
   - Translate Rust/LLVM relocation types into udynlink relocation types
   - **This is the hardest part and depends on the Phase 0 spike results**

4. **Build LOT**
   - Map each unique relocated symbol to a LOT index
   - For local/exported symbols: LOT entry will be patched with absolute address at load time
   - For external symbols: LOT entry will be patched with resolved host address at load time

5. **Patch code**
   - For each relocation, patch the instruction in `.text` to reference the LOT index instead of the original address/GOT entry
   - **Depends on the instruction encoding for the chosen relocation model**

6. **Generate symbol table**
   - Same format as C modules: (name_offset, value) pairs with type/location encoding
   - Module name is first entry
   - Exported functions have their VALUE = offset in `.text` (accounting for prologue)
   - External functions have VALUE = 0 (resolved at load time)

7. **Assemble binary**
   - Write header
   - Write relocations
   - Write symbol table
   - Write dependency string table (if module declares deps)
   - Write `.text` + `.data`

### 5.3 Relocation Mapping (Tentative — Depends on Spike)

| Rust/LLVM Type | Description | udynlink Action |
|----------------|-------------|-----------------|
| `R_ARM_GOT_BREL` | GOT entry offset from static base | Map to LOT offset, patch code |
| `R_ARM_GOT_PREL` | GOT entry offset from PC | Map to LOT offset, patch code |
| `R_ARM_ABS32` | Absolute 32-bit address | Map to data relocation |
| `R_ARM_SBREL32` | Offset from static base (r9) | Map to LOT offset |
| `R_ARM_TARGET1` | Platform-specific (often ABS32) | Same as ABS32 |
| `R_ARM_THM_CALL` / `R_ARM_THM_JUMP24` | PC-relative call | Ignore (same as C) |
| `R_ARM_MOVW_ABS_NC` / `R_ARM_MOVT_ABS` | Absolute address in movw/movt pair | Complex — may need special handling |

### 5.4 Handling `.rodata` Mismatch

C modules merge `.rodata` into `.text`. Rust keeps `.rodata` separate. The post-processor MUST either:
- Merge `.rodata` into `.text` (append after code), OR
- If the linker script already does this, rely on that

**Recommendation:** Provide a custom linker script for Rust modules that merges `.rodata` into `.text`, just like `code_before_data.ld` does for C.

### 5.5 Handling Data Relocations (`R_ARM_ABS32`)

In C modules, `R_ARM_ABS32` typically appears in `.data` for things like:
```c
static int *ptr = &global_var;   // ptr needs absolute address of global_var
```

The existing loader patches `.data` words at load time. The Rust post-processor must:
- Identify `R_ARM_ABS32` relocations in `.data`
- Add them to the relocation table with the appropriate lot_offset (pointing past the LOT into `.data`)
- Set the symt_offset to the symbol index

## 7. Difficulty & Tradeoff Analysis

### 7.1 Hardest Problem: Relocation Compatibility

**Difficulty: HIGH**

The existing udynlink loader was designed around GCC's `-msingle-pic-base` model, which consistently generates `R_ARM_GOT_BREL` relocations. Rust/LLVM might generate a different relocation model.

**Scenarios:**

| Scenario | Feasibility | Mitigation |
|----------|-------------|------------|
| Rust `pic` generates `R_ARM_GOT_BREL` | ✅ Easy | Post-processor works like mkmodule |
| Rust `pic` generates `R_ARM_GOT_PREL` (PC-relative GOT) | ⚠️ Medium | Need to rewrite PC-relative loads to r9-relative LOT access; possible if GOT is placed at fixed offset |
| Rust `pic` uses absolute GOT addresses (no reloc) | ❌ Blocker | Cannot post-process; must change compiler flags |
| Rust `static` generates no relocations | ❌ Hard | Need to restrict module code to have no globals; or use custom LOT discipline in Rust source |
| Rust `ropi-rwpi` works | ⚠️ Medium | Would work, but requires extending C loader; user said don't modify loader |

**Mitigation strategy:**
- Phase 0 spike determines exact feasibility
- If primary model fails, investigate cargo rustc + LLVM flags to force specific relocation types
- If all else fails, fall back to a "manual LOT" model where `udynlink-module` crate provides a static LOT and proc-macro transforms data access to use it

### 7.2 Prologue Injection

**Difficulty: MEDIUM**

The C toolchain generates assembly prologues as separate `.s` files and links them. For Rust, we need an equivalent mechanism.

**Options:**
1. **Proc-macro generates `.s` file at compile time**: Complex, needs build.rs integration
2. **Proc-macro uses inline asm**: Portable but fragile around calling conventions
3. **Post-processor generates `.s` after compilation**: Cleanest — Rust compiles normally, tool generates wrappers

**Recommended:** Option 3 (post-processor generates wrappers), same as C toolchain. The proc-macro only emits metadata to a custom ELF section.

### 7.3 `.rodata` Placement

**Difficulty: LOW**

Rust keeps `.rodata` separate. Udynlink expects it merged into `.text` (or accessible via fixed offsets).

**Solution:** Custom linker script `udynlink.ld` that merges `.rodata` into `.text`.

### 7.4 Vtables and Dynamic Dispatch

**Difficulty: MEDIUM (restriction)**

Rust trait objects (`dyn Trait`) generate vtables in `.data` with absolute function pointers (rust#54431). These vtables are non-PIC and cannot be relocated by the existing udynlink loader without changing their contents.

**Solution:** Document that `dyn Trait` is not supported in udynlink modules. Static dispatch and generic monomorphization work fine.

### 7.5 Panic Handling

**Difficulty: LOW**

Each `no_std` Rust binary needs a panic handler. `udynlink-module` provides a default abort-on-panic handler. Module authors can override it.

### 7.6 Stack Usage

**Difficulty: LOW**

The assembly prologue pushes 2-4 registers. This adds ~16 bytes of stack per module call. This is acceptable for embedded but should be documented.

## 9. Risk Register

| Risk | Likelihood | Impact | Strategy |
|------|-----------|--------|----------|
| No Rust relocation model produces mappable relocations | Medium | Blocker | Phase 0 spike detects this early. Fallback: extend C loader (requires user approval). |
| rust-lld rejects PIC/PIE on bare metal | Low | High | Use GNU ld via `-C linker=arm-none-eabi-ld` if needed. |
| Proc-macro meta-section not preserved by rust-lld | Low | Medium | Test early; use `.comment` or `.note` sections as fallback. |
| Inline asm prologue breaks Rust calling convention | Medium | Medium | Test with variadic args, structs, floats. Use separate `.s` files if needed. |
| `dyn Trait` / vtables non-relocatable | High | Medium | Document restriction. Static generics work fine. |
| Multi-arch proc-macro (ARMv6m vs v7m vs v8m) | Medium | Low | Three asm templates exist; proc-macro/CLI must select correct one. |

## 10. Open Questions (for Implementation Agents)

1. **Can Phase 0 be done in parallel with Phase 1 (crate skeleton)?** Yes — the spike is read-only and the crate skeleton doesn't depend on relocation model.
2. **Should `udynlink-module` support `core::fmt` (format strings)?** `core::fmt` uses large trait infrastructure and panics on some errors. Recommend avoiding in v1; document alternatives.
3. **Should the tool be written in Rust or Python?** Rust is idiomatic for the crate ecosystem. Python (extending `mkmodule`) would share more code with existing toolchain. **Recommendation:** Rust for the standalone tool, Python integration later for `mkmodule` parity.
